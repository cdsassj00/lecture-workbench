에이전트 아키텍처

서브에이전트 vs 멀티에이전트
— 코딩 몰라도 이해하는 완전 가이드

AI 에이전트를 여러 개 쓰는 방법에 대해 "서브에이전트"와 "멀티에이전트"라는 말을 자주 듣게 됩니다. 둘 다 "에이전트를 여러 개 쓰는 것" 같아 보이지만, 구조·목적·활용법이 다릅니다. 기초 개념부터 실제 사례까지, 차근차근 설명합니다.

1. 에이전트(Agent)가 뭔가요?

먼저 "에이전트"가 뭔지부터 정리해야 합니다. AI 에이전트는 단순히 질문에 답하는 것을 넘어, 스스로 판단하고 행동하는 AI입니다.

❌ 일반 AI (챗봇)

  • 질문 → 답변 (그것으로 끝)
  • 파일을 직접 수정하지 못함
  • 인터넷 검색 못함
  • 터미널 명령 실행 못함
  • 한 번 대화로 끝남

✅ AI 에이전트

  • 목표를 받으면 스스로 계획 수립
  • 파일 읽기·수정·생성 직접 수행
  • 인터넷 검색, API 호출 가능
  • 터미널 명령 실행 가능
  • 목표 달성까지 반복적으로 수행
비유: 일반 AI는 "질문에 답하는 백과사전"이고, AI 에이전트는 "업무를 직접 처리하는 직원"입니다. "보고서 써줘" 라고 하면 백과사전은 쓰는 법을 알려주지만, 에이전트는 직접 자료를 찾아서 보고서를 완성해 줍니다.

2. 왜 에이전트를 여러 개 쓰나요?

에이전트 하나로는 한계가 있습니다.

한계설명실제 문제 상황
컨텍스트 창 한계 한 번에 볼 수 있는 텍스트 양이 제한됨 파일 수천 개짜리 코드베이스 전체를 한 번에 분석 불가
전문성 한계 하나의 에이전트가 모든 분야를 다 잘하기 어려움 코딩·보안·문서화를 동시에 완벽하게 처리하기 어려움
병렬 처리 불가 에이전트 하나는 한 번에 하나씩만 처리 100개 파일을 순서대로 분석하면 시간이 너무 오래 걸림
자기 검증 한계 스스로 만든 것의 오류를 잘 못 잡음 자신이 생성한 코드의 버그나 논리 오류를 놓칠 수 있음

이 한계를 극복하기 위해 에이전트를 여러 개 쓰는 방식이 등장했습니다. 그게 바로 서브에이전트와 멀티에이전트 시스템입니다.

핵심 관계 정리 (먼저 알고 시작):

멀티에이전트 시스템 = "여러 에이전트가 함께 동작하는 모든 시스템"의 총칭
서브에이전트 구조 = 멀티에이전트 시스템 중 "오케스트레이터 + 하위 에이전트" 계층형 구조

즉, 서브에이전트는 멀티에이전트의 한 종류입니다.
"강아지는 동물이다" 처럼, "서브에이전트 구조는 멀티에이전트 시스템이다"라고 볼 수 있습니다.

3. 서브에이전트(Subagent)란?

쉽게 이해하기

서브에이전트는 "팀장(오케스트레이터)이 팀원(서브에이전트)들에게 업무를 나눠서 시키는 구조"입니다.

🏢 회사 조직 비유:

오케스트레이터 = 팀장. "이번 프로젝트를 완성해야 해"라는 큰 목표를 받음.
→ 팀장은 혼자 다 하지 않고, 전문 팀원들에게 나눠서 맡깁니다:

  • 서브에이전트 A (코드 리뷰어): "너는 코드 품질 검토해"
  • 서브에이전트 B (보안 검사자): "너는 보안 취약점 찾아"
  • 서브에이전트 C (문서 작성자): "너는 변경사항 문서화해"

팀장은 각 팀원의 결과를 모아서 최종 보고서를 작성합니다.
팀원들은 서로 직접 대화하지 않고, 팀장을 통해서만 소통합니다.

구조와 흐름

서브에이전트 구조 (계층형 · 위임형)
🎯 오케스트레이터 (메인 에이전트)
전체 목표 수신 → 작업 분배 → 결과 통합
🔍 서브에이전트 A
코드 리뷰 전문
🛡️ 서브에이전트 B
보안 검사 전문
📝 서브에이전트 C
문서 작성 전문
화살표 방향: 오케스트레이터 → 서브에이전트 (위에서 아래로 단방향)
서브에이전트끼리는 직접 소통하지 않습니다.

서브에이전트 구조의 핵심 특징 3가지:

  1. 반드시 오케스트레이터(지휘자)가 있다
    모든 작업은 오케스트레이터가 받아서 분배합니다. 서브에이전트끼리 직접 대화하거나 독립적으로 행동하지 않습니다. 오케스트레이터가 전체 흐름을 통제합니다.
  2. 각 서브에이전트는 전문 역할이 고정된다
    코드 리뷰어는 코드 리뷰만, 테스트 작성자는 테스트만 합니다. 역할이 명확하게 분리되어 있기 때문에 더 전문적인 결과를 만들 수 있습니다.
  3. 병렬 실행이 가능하다
    A, B, C가 동시에 각자 일을 할 수 있습니다. 오케스트레이터는 모두 완료되면 결과를 합칩니다. 순서대로 하는 것보다 훨씬 빠릅니다.

오케스트레이터(Orchestrator)가 하는 일

오케스트레이터는 단순히 "시키는" 역할이 아닙니다. 꽤 많은 일을 합니다.

역할설명예시
목표 해석사용자의 큰 요청을 분석"전체 코드베이스 리팩토링" 요청을 받음
작업 분해큰 일을 서브 태스크로 쪼갬리뷰 / 테스트 / 문서화 / 최적화로 나눔
에이전트 선택각 태스크에 맞는 서브에이전트 결정"이건 보안 전문 에이전트한테 맡겨야 해"
결과 수집모든 서브에이전트 결과를 취합리뷰 결과 + 보안 보고서 + 문서 통합
충돌 해결서브에이전트 간 결과 충돌 조율"A는 이걸 삭제하라는데 B는 유지하라네"
최종 전달통합된 결과를 사용자에게 반환최종 PR 리뷰 리포트 작성

장점과 한계

✅ 서브에이전트의 장점

  • 메인 컨텍스트 보호
    서브에이전트가 파일 1000개를 뒤져도 메인 대화에 영향 없음
  • 병렬 처리
    A, B, C가 동시에 작업 → 3배 빠름
  • 전문화
    각자 자기 분야만 깊이 파고듦
  • 재사용성
    코드 리뷰어를 다른 프로젝트에도 사용
  • 예측 가능성
    오케스트레이터가 전체 흐름을 통제하므로 예측 가능

⚠️ 서브에이전트의 한계

  • 오케스트레이터 병목
    오케스트레이터가 잘못 판단하면 전체 실패
  • 서브에이전트 간 소통 없음
    A가 B의 결과를 모름. 오케스트레이터만 앎
  • 유연성 부족
    역할이 고정되어 있어 예상 밖 상황에 약함
  • 단일 장애점
    오케스트레이터가 실패하면 전체 시스템 멈춤

Claude Code 서브에이전트 실제 예시

Claude Code에서 서브에이전트는 .claude/agents/ 폴더에 마크다운 파일로 정의합니다. 이름, 역할 설명, 사용 가능한 도구, 모델을 지정합니다.

# .claude/agents/code-reviewer.md
---
name: code-reviewer
description: 코드 리뷰. 스타일, 보안, 성능 문제 체크. 심각도 분류.
tools: Read, Grep, Glob
model: claude-sonnet-4-6
---

당신은 코드 리뷰 전문 에이전트입니다.
다음 기준으로 리뷰하세요:
  1. 보안 취약점 (SQL 인젝션, XSS, 노출된 키 등)
  2. 성능 문제 (N+1 쿼리, 불필요한 루프 등)
  3. 코드 스타일 (네이밍, 함수 길이, 중복 코드)

결과를 심각도 상/중/하로 분류해서 보여주세요.
# .claude/agents/test-writer.md
---
name: test-writer
description: 테스트 코드 작성. 단위 테스트 + 엣지케이스 포함.
tools: Read, Write, Bash(npm test:*)
model: claude-sonnet-4-6
---

당신은 테스트 작성 전문가입니다.
- 단위 테스트는 Vitest로 작성
- 엣지케이스 반드시 포함
- 테스트 실행까지 확인
실제 사용법:
사용자: "이 PR 코드 리뷰해줘"
→ 오케스트레이터(Claude)가 판단: "이건 code-reviewer 서브에이전트 쓸 상황이군"
→ code-reviewer 자동 호출 — 전용 컨텍스트에서 독립적으로 작업
→ 리뷰 결과만 오케스트레이터에게 반환 (메인 대화 오염 없음)

실제 동작 흐름 — 단계별

== 사용자 요청 ==
사용자: "이번 커밋의 코드를 리뷰하고 테스트도 보강해줘"

== Step 1: 오케스트레이터가 작업 분해 ==
오케스트레이터 판단:
  - 코드 변경사항 파악    → 내가 직접 처리
  - 코드 품질 리뷰         → code-reviewer 에게 위임
  - 부족한 테스트 보강     → test-writer 에게 위임
  - 결과 통합 및 보고      → 내가 직접 처리

== Step 2: 병렬 실행 ==
[code-reviewer 실행 중...]       [test-writer 실행 중...]
  src/auth.ts 분석 중...           기존 테스트 파악 중...
  보안 취약점 2개 발견             누락 케이스 3개 발견
  심각도 분류 완료                 테스트 코드 작성 완료
  → 결과 반환                      → 결과 반환

== Step 3: 오케스트레이터가 결과 통합 ==
"리뷰 결과: 보안 문제 2건 (중요도 상), 스타일 5건..."
"테스트 추가: auth.test.ts 에 3개 케이스 추가됨"
→ 최종 통합 리포트를 사용자에게 전달

4. 멀티에이전트(Multi-agent)란?

쉽게 이해하기

멀티에이전트 시스템은 "여러 AI 에이전트가 함께 동작하는 모든 시스템"을 가리키는 포괄적인 용어입니다. 서브에이전트 구조도 멀티에이전트의 한 형태지만, 에이전트들이 수평적으로 협력하거나, 순서대로 결과를 넘기거나, 서로 경쟁하는 구조도 모두 멀티에이전트입니다.

🏥 병원 진료 비유:

어떤 환자가 복잡한 병을 앓고 있습니다. 한 명의 의사로는 부족합니다.

서브에이전트 방식 (계층형):
주치의(오케스트레이터)가 "내과는 네가, 외과는 네가, 영상의학은 네가 담당해"라고 지시. 각 전문의는 주치의의 지시에 따라 독립적으로 검사 후 주치의에게 결과 보고.

멀티에이전트 방식 (수평형):
내과·외과·영상의학과 의사들이 함께 회의실에 모여 서로 의견을 나누고, 어떤 진단이 맞는지 토론해서 결론 도출. 누가 지휘자가 아님.

→ 둘 다 "여러 전문가가 협력하는" 것이지만, 지시 구조의 위치가 다릅니다.

멀티에이전트의 4가지 대표 유형

멀티에이전트 시스템은 에이전트들이 어떻게 연결되는지에 따라 크게 4가지로 나뉩니다.

① 계층형 (= 서브에이전트 구조)

계층형 멀티에이전트 = 서브에이전트 구조
오케스트레이터
에이전트 A
에이전트 B
에이전트 C
지시는 위에서 아래로. 서브에이전트끼리 직접 소통 없음.
특징: 오케스트레이터가 모든 것을 통제. 예측 가능하고 디버깅 쉬움.
쓸 때: 큰 작업을 전문화된 팀원들에게 나눠 맡길 때
예시: Claude Code 서브에이전트, PR 리뷰 자동화 시스템

② 수평형 (피어-투-피어, 협력형)

수평형 멀티에이전트 — 에이전트들이 대등하게 협력
에이전트 A
분석 담당
⇄
에이전트 B
비판 담당
⇄
에이전트 C
종합 담당
누구도 지휘자가 아님. 서로 대화하고 의견 교환. 양방향 소통.
특징: 에이전트들이 서로의 출력을 보고 피드백. 상호 검증으로 오류 감소.
쓸 때: 한 에이전트가 틀릴 수 있어서 여러 관점으로 검증이 필요할 때
예시: AI 논문 리뷰 시스템, 법률 문서 검토, 사실 검증 에이전트 네트워크

③ 파이프라인형 (순차 연결)

파이프라인형 멀티에이전트 — 순서대로 결과를 다음 에이전트에게 넘김
에이전트 A

A의 출력이 B의 입력. B의 출력이 C의 입력. 컨베이어 벨트처럼 순서대로.
특징: 각 에이전트가 이전 단계 결과를 받아서 처리. 단계별 변환에 최적.
쓸 때: 데이터 수집 → 분석 → 요약처럼 단계가 명확할 때
예시: 뉴스 수집 → 번역 → 요약 → 발송 파이프라인, ETL 자동화

쓸 때: 정답이 하나가 아니거나, 최선을 골라야 할 때
예시: AlphaCode (여러 코드 생성 후 테스트 통과한 것 선택), AI 채점 시스템

멀티에이전트 전체 장점과 한계

✅ 멀티에이전트의 장점

  • 확장성: 에이전트를 추가해서 능력 확장
  • 상호 검증: 여러 에이전트가 서로 오류 잡음
  • 다양한 구조: 문제에 맞게 구조 선택 가능
  • 복잡한 문제 해결: 하나로 못 풀 때 강력
  • 장애 내성: 하나 실패해도 다른 것이 커버

⚠️ 멀티에이전트의 한계

  • 비용 증가: 에이전트 수만큼 API 비용 증가
  • 조율 복잡성: 에이전트 간 통신 관리 어려움
  • 디버깅 어려움: 어느 에이전트가 틀렸는지 파악 힘듦
  • 지연 증가: 에이전트 간 통신으로 속도 저하
  • 충돌 해결 필요: 에이전트들이 서로 다른 답 낼 때

5. 핵심 차이점 — 완전 비교표

비교 항목서브에이전트멀티에이전트 (수평형 기준)
포함 관계 멀티에이전트의 한 종류 (부분집합) 상위 개념. 서브에이전트를 포함함
구조 형태 트리형 — 1개 오케스트레이터 + N개 하위 에이전트 네트워크형 — 에이전트들이 서로 연결
지휘 방식 중앙집중 — 오케스트레이터가 모든 것 결정 분산 — 에이전트들이 스스로 판단·협의
통신 방향 위 → 아래 (단방향) 양방향, 다방향 (모든 에이전트 간 가능)
에이전트 자율성 낮음 — 지시받은 것만 수행 높음 — 스스로 판단하고 행동
역할 유연성 고정 — "코드 리뷰어"는 항상 코드 리뷰만 유동 — 상황에 따라 역할 변화 가능
예측 가능성 높음 — 오케스트레이터가 흐름 통제 낮음 — 에이전트 간 상호작용 예측 어려움
구현 난이도 상대적으로 쉬움 복잡도 높음 (통신 프로토콜 설계 필요)
주요 강점 전문화, 병렬 처리, 컨텍스트 보호 상호 검증, 집단 지성, 복잡 문제 해결
주요 약점 오케스트레이터 단일 장애점 비용 증가, 디버깅 어려움
비유 팀장이 팀원에게 업무 분배 여러 전문가가 회의에서 협력
대표 사례 Claude Code 서브에이전트 AI 논문 리뷰, 팩트체크 시스템

6. 언제 무엇을 써야 해?

서브에이전트가 적합한 상황

상황이유예시
큰 작업을 역할 분리해서 처리하고 싶을 때 오케스트레이터가 분해하고 위임하기 좋음 코드 리뷰 + 테스트 + 문서화 동시에
메인 대화 오염 없이 세부 작업을 처리할 때 서브에이전트는 별도 컨텍스트 사용 1000개 파일 검색, 메인엔 결과만 반환
같은 에이전트를 여러 프로젝트에서 재사용 역할이 고정되어 있어 재사용하기 좋음 코드 리뷰어를 모든 프로젝트에 적용
병렬 처리로 속도를 높이고 싶을 때 여러 서브에이전트가 동시에 작업 가능 10개 파일을 10개 에이전트가 동시 분석
흐름을 정확히 제어하고 싶을 때 오케스트레이터가 모든 것을 통제 단계별 승인이 필요한 업무 프로세스

수평형 멀티에이전트가 적합한 상황

상황이유예시
한 에이전트의 판단을 검증해야 할 때 다른 에이전트가 오류를 잡아줄 수 있음 의료 진단, 법률 해석, 재무 분석
여러 관점이 필요한 복잡한 결정 각자 다른 시각으로 기여 전략 수립, 리스크 평가
정답이 불명확하고 토론이 필요할 때 에이전트들이 서로 반론하며 발전 새로운 아이디어 검토, 창작물 평가

파이프라인형이 적합한 상황

데이터가 단계별로 변환되어야 할 때 씁니다.
원본 데이터 → 전처리 → 분석 → 시각화 → 보고서처럼 입력과 출력이 명확한 단계가 이어질 때 최적입니다.

핵심 판단 질문: "이전 단계의 결과물이 다음 단계의 원료가 되는가?" → 파이프라인형

7. 실전 시나리오로 이해하기

시나리오 A — 소프트웨어 개발팀의 PR 리뷰

새로운 결제 기능을 개발했고, PR을 올리기 전에 검토가 필요합니다. 어떤 방식이 더 어울릴까요?

🎯 서브에이전트 방식 선택

  • 오케스트레이터: PR 분석 후 작업 분배
  • 코드 리뷰어: 코드 품질 체크 (병렬)
  • 보안 에이전트: 결제 로직 보안 검토 (병렬)
  • 테스트 에이전트: 테스트 커버리지 확인 (병렬)
  • 오케스트레이터: 결과 통합 → 최종 리포트
✅ 각 분야 전문화, 병렬 처리로 빠름

🤝 수평형은 언제?

  • "이 결제 방식 자체가 맞나?" 같은 질문
  • 아키텍처 트레이드오프 결정
  • 정답이 없는 설계 방향 선택
  • 에이전트들이 서로 의견 교환
  • 합의된 최종 방향 도출
✅ 복잡한 결정, 다양한 관점 필요할 때
결론: PR 검토처럼 각 항목을 독립적으로 체크할 수 있는 작업은 서브에이전트가 빠르고 효율적입니다. 반면 "이 아키텍처 방향이 맞나?"처럼 정답이 없고 토론이 필요한 결정은 수평형 멀티에이전트가 더 적합합니다.

시나리오 B — 리서치 보고서 자동 생성

== 파이프라인형 멀티에이전트 예시 ==

사용자: "AI 반도체 시장 동향 보고서 만들어줘"

에이전트 A (수집):
  → 최신 뉴스, 논문, 시장조사 자료 크롤링
  → 원본 데이터 100개 수집
  → 결과물: raw_data.json

에이전트 B (분석):  ← A의 raw_data.json 을 입력으로 받음
  → 핵심 트렌드 5가지 추출
  → 수치 데이터 정리
  → 결과물: analysis.json

에이전트 C (작성):  ← B의 analysis.json 을 입력으로 받음
  → 보고서 형식으로 문서화
  → 그래프 및 표 포함
  → 결과물: report.pdf
파이프라인형은 각 에이전트가 이전 단계의 출력을 입력으로 받는 구조입니다. 서브에이전트와 비슷해 보이지만, 오케스트레이터가 통제하는 게 아니라 에이전트들이 순서대로 자동 연결된다는 점이 다릅니다.

시나리오 C — AI 논술 채점 시스템

== 경쟁형 멀티에이전트 예시 ==

문제: "이 학생의 서술형 답안을 100점 만점으로 채점하라"

에이전트 A (독립적으로 채점): 62점 — 논리 구조가 약함
에이전트 B (독립적으로 채점): 70점 — 창의성은 있으나 근거 부족
에이전트 C (독립적으로 채점): 65점 — 전반적으로 평균 수준

→ 평균: 65.7점
→ 각 에이전트 근거를 비교해서 최종 점수 결정
→ 최종: 66점 (근거 포함 상세 피드백)
경쟁형은 한 에이전트의 판단만 믿기 어려울 때 씁니다. 여러 에이전트가 독립적으로 같은 문제를 풀고, 결과를 비교해서 신뢰성을 높입니다. 의료 진단, 법률 해석, 심사 평가 등 중요한 판단에 유용합니다.

8. 함께 쓰기 — 실제 고급 시스템

실제 복잡한 AI 시스템에서는 서브에이전트와 멀티에이전트를 혼합합니다. 오케스트레이터가 서브에이전트들을 호출하고, 그 서브에이전트들이 내부에서 멀티에이전트 방식으로 협력하는 구조입니다.

혼합형 — 계층형 + 수평 협력 조합
🎯 오케스트레이터
전체 목표 조율 · 결과 통합
서브에이전트 그룹 (내부에서 상호 협력)
분석 에이전트
⇄
비판 에이전트
⇄
검증 에이전트
오케스트레이터는 전체를 통제하지만, 서브에이전트들끼리는 수평적으로 협력
== 혼합형 실전 예시: 복잡한 아키텍처 설계 ==

사용자: "우리 서비스를 마이크로서비스로 전환하는 계획 세워줘"

오케스트레이터:
  "이건 혼자 처리하기엔 복잡해. 설계 팀 만들자."

  → 서브에이전트 그룹 실행 (내부에서 멀티에이전트 협력)
  설계A: "이렇게 서비스를 8개로 분리하자" (초안 제안)
  비판B: "결제와 재고가 같은 DB면 데이터 정합성 문제 생겨" (반론)
  설계A: "그럼 Saga 패턴 적용하면 어때?" (수정안)
  검증C: "마이그레이션 비용과 기간은 얼마나 될까?" (검증)
  비판B: "6개월은 너무 위험해. 단계적 전환 방식은?" (재반론)
  설계A + 검증C: "Strangler Fig 패턴으로 단계별 전환 동의" (합의)

오케스트레이터:
  "그룹 토론 완료. 결론: Strangler Fig 패턴 12개월 전환 계획"
  → 사용자에게 최종 계획서 전달

9. 자주 묻는 질문 (FAQ)

Q. 서브에이전트랑 멀티에이전트가 같은 말 아닌가요?
다릅니다. 멀티에이전트는 "여러 에이전트가 함께 쓰이는 모든 시스템"을 가리키는 넓은 개념입니다. 서브에이전트는 그 중 "오케스트레이터가 하위 에이전트에게 위임하는 계층형 구조"를 가리킵니다. 관계를 정리하면: 서브에이전트 ⊂ 멀티에이전트.

즉, 모든 서브에이전트 시스템은 멀티에이전트 시스템이지만, 모든 멀티에이전트 시스템이 서브에이전트 구조인 건 아닙니다.
Q. 그냥 에이전트 하나로 하면 안 되나요?
작은 작업은 하나로 충분합니다. 하지만 큰 코드베이스 전체를 분석하거나, 여러 전문 분야를 동시에 처리하거나, 상호 검증이 필요한 경우에는 에이전트 하나로는 컨텍스트 한계나 전문성 한계에 부딪힙니다. 그럴 때 여러 에이전트를 씁니다. 반대로, 단순한 작업에 복잡한 멀티에이전트 시스템을 쓰는 건 과도한 비용과 복잡성만 초래합니다.
Q. 에이전트가 많을수록 항상 좋은 건가요?
아닙니다. 에이전트 수가 늘수록 API 비용이 증가하고, 조율이 복잡해지며, 디버깅이 어려워집니다. 단순한 작업에 복잡한 멀티에이전트 시스템을 쓰는 건 오히려 역효과입니다. "최소한의 에이전트로 최대한의 효과"가 실제 시스템 설계의 원칙입니다.
Q. Claude Code에서 멀티에이전트는 어떻게 구현하나요?
Claude Code는 기본적으로 서브에이전트 구조를 지원합니다 (.claude/agents/ 폴더에 에이전트 정의). 수평형 멀티에이전트는 MCP(Model Context Protocol)를 통해 외부 에이전트 시스템과 연결하거나, 오케스트레이터가 여러 에이전트를 순차적으로 호출하고 결과를 다시 다음 에이전트에게 넘기는 방식으로 구현할 수 있습니다.
Q. A2A(Agent-to-Agent) 프로토콜과는 어떤 관계인가요?
A2A는 Google이 제안한 에이전트 간 통신 표준입니다. 이 프로토콜을 쓰면 서로 다른 AI 에이전트들이 표준화된 방식으로 소통할 수 있습니다. 수평형 멀티에이전트를 실제로 구현할 때 A2A를 통신 레이어로 사용합니다. 즉, A2A는 멀티에이전트 시스템을 실제로 연결하는 "통신 인프라"입니다. MCP가 "에이전트와 외부 도구를 연결"한다면, A2A는 "에이전트와 에이전트를 연결"합니다.
Q. 오케스트레이터도 AI 에이전트인가요?
네. 오케스트레이터도 AI 에이전트입니다. Claude Code에서는 Claude 자체가 오케스트레이터 역할을 합니다. 사용자의 요청을 받아서 어느 서브에이전트를 호출할지 판단하고, 결과를 통합하는 일 자체가 AI 에이전트의 역할입니다. 즉, 오케스트레이터는 "서브에이전트들을 관리하는 상위 AI 에이전트"입니다.

서브에이전트 오케스트레이터가 하위 에이전트에게 일을 위임 계층형 (트리) 전문화, 병렬, 컨텍스트 보호 팀장 → 팀원

멀티에이전트 (파이프) 에이전트들이 순서대로 결과를 넘김 파이프라인형 단계별 변환, 명확한 흐름 컨베이어 벨트
멀티에이전트 (경쟁) 독립적으로 풀고 최선 선택 병렬 독립형 강건성, 신뢰성 여러 의사 소견

서브에이전트 = 오케스트레이터 + 하위 에이전트의 계층형 위임 구조

작업 분업·병렬 처리가 필요하다 → 서브에이전트
